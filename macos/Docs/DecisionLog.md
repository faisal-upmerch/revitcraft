# Decision log

Short records of decisions that shape Arcus, newest last. Each entry gives the decision, why it was made, and what it costs.

### D1. SwiftPM package staged into an app bundle, not an Xcode project
- **Decision:** One `Package.swift` builds every module. `script/build_and_run.sh` stages `build/Arcus.app` (Info.plist with version and build substituted, icon, ad-hoc signature) and validates it.
- **Why:** Builds are reproducible from the command line with the Apple toolchain only, strict module boundaries are enforced, and there are no project-file merge conflicts. It also works headless for tests and benchmarks.
- **Cost:** No Xcode asset catalogs or XCUITest target. The icon is generated to `.icns` by a script, and UI QA uses the in-app harness (see `Arcus/UITests/README.md`).

### D2. Layered modules with a value-type model
- **Decision:** Geometry and Calc sit under Domain, which sits under Application, which sits under UI. Infrastructure depends only on Domain. `BIMModel` is an immutable-by-convention `Sendable` value snapshot.
- **Why:** Background work (view builds, export, save, schedules) gets consistent snapshots without locks. It also makes undo and crash recovery straightforward, and the engine can be tested without UI.
- **Cost:** Each commit copies the element dictionary. That is cheap in practice because of copy-on-write buckets: about 0.3 ms per transaction on the reference project and about 6 ms on 20,000 elements.

### D3. Transactions store full before/after elements
- **Decision:** `TransactionRecord` stores the complete before and after `Element` for every touched id. Undo applies the inverse record.
- **Why:** Undo is exact and O(changed elements) for every kind of edit, including regeneration side effects. The same records feed the crash-recovery journal.
- **Cost:** Records are larger than parameter diffs. Undo history is capped at 200 levels.

### D4. Derived geometry is never persisted
- **Decision:** Wall joins, solids, room boundaries, family geometry and view graphics are recomputed on demand and cached by input revisions.
- **Why:** The file format stays small and stable, stale geometry can't be saved, and geometry fixes apply to old files automatically.
- **Cost:** A project's first open computes geometry lazily. Caches must key on every real input: `DependencyGraph.inputs` defines them, and tests cover invalidation.

### D5. Native Swift IFC and geometry, no third-party kernel
- **Decision:** A STEP reader and writer, the IFC mapping, polygon booleans, hidden-line removal and the roof solver are all written in Swift.
- **Why:** Licensing (the candidates are LGPL or MPL, or have unclear licences), plus a single-bundle distribution with strict concurrency and deterministic output for golden tests. See [EngineDecision.md](EngineDecision.md).
- **Cost:** The IFC scope is the architectural subset. Unsupported entities are imported as reference geometry. There is no general B-rep kernel, so solids are extrusions, sweeps and tessellated meshes.

### D6. DWG only through a licensed SDK, behind a provider seam
- **Decision:** `DWGImportProvider` has an ODA-backed implementation that compiles only with `ARCUS_ODA_SDK_DIR`, and an `UnavailableDWGProvider` that explains the situation truthfully. `ARCUS_REQUIRE_DWG=1` makes the build fail with setup steps when the SDK is missing.
- **Why:** DWG is proprietary. Faking support, or renaming DXF to DWG, would mislead users, and vendor binaries cannot be committed.
- **Cost:** The ODA bridge (`DWGBridge`) could not be compiled or verified here without a licensed SDK. It is marked unverified in [DWGSDKSetup.md](DWGSDKSetup.md).

### D7. SQLite package format with a manifest and checksums
- **Decision:** `.arcus` is a directory package containing `model.sqlite` (one versioned JSON row per element), `manifest.json` (schema version, minimum reader version, SHA-256 checksums) and a thumbnail. Saves go through NSDocument safe-save.
- **Why:** Atomic replacement, incremental reads, readable diagnostics, forward and backward version gates, and salvaging damaged files element by element.
- **Cost:** Packages are directories. Sharing them by email needs zipping, which Finder does.

### D8. Crash recovery through a journal, separate from autosave
- **Decision:** NSDocument autosaves in place. Separately, `RecoveryJournal` keeps a base snapshot plus an append-only log of transaction records under Application Support, replayed after a crash.
- **Why:** Recovery never overwrites the user's file, and recovered changes open as a new unsaved window. The journal survives a crash between autosaves.
- **Cost:** Extra disk writes per transaction. They are small, and a serialized queue keeps them off the main thread.

### D9. CoreGraphics 2D canvas and a Metal 3D viewport
- **Decision:** 2D views draw cached vector display lists with CoreGraphics. 3D uses a custom Metal renderer.
- **Why:** The same display lists render the screen and the vector PDF, so what you print is what you see. CoreGraphics gives exact hairlines, patterns and text. Metal handles tens of thousands of elements at interactive rates.
- **Cost:** 2D redraws are CPU-bound. Display lists are built off the main actor, and hit testing uses a spatial grid.

### D10. Command catalog as the single source for commands
- **Decision:** `CommandCatalog` defines every command's title, group, symbol, shortcut, aliases and help. Menus, the Command Deck, Command Search, context menus and the shortcut documentation are all generated from it.
- **Why:** Consistency, and nothing drifts between the UI and the docs.

### D11. In-app QA harness instead of XCUITest
- **Decision:** `--qa workflow|screenshots` runs scripted end-to-end scenarios inside the app and reports JSON. Screenshots come from window ids through `screencapture`, plus in-process rendering.
- **Why:** It works without an Xcode project or an Accessibility-permissioned runner, is deterministic, and asserts on model state rather than on pixels.
- **Cost:** It does not exercise real mouse event delivery. Manual QA covered pointer interactions.

### D12. Spatial plan grid and content stamps in `BIMModel` (performance)
- **Decision:** `BIMModel` keeps a sparse 8 m plan grid over linear elements and a process-unique `contentStamp` per snapshot.
- **Why:** Benchmarks on the 20,000-element fixture showed O(n²) wall-join lookups (plan graphics 13.7 s, all meshes 13.9 s, moving all walls 37.8 s). With the grid these became 0.12 s, 0.08 s and 0.10 s. Room-boundary cache keys were rebuilt by hashing the whole model on every lookup; with stamps they are computed once per snapshot. See [Performance.md](Performance.md).

### D13. Parameter fast paths for schedules and tags
- **Decision:** Schedules and tags look up one parameter (`descriptor(named:)`, `value(_:of:)`, `isEditable`) instead of building every parameter entry.
- **Why:** Building all entries evaluated costly derived parameters, such as From/To Room, for every cell. The Door Schedule dropped from 257 ms to 9 ms, and the Ground Floor plan from 58 ms to 5 ms. A test checks that the fast paths agree with the full entries for every parameter on a sample of 120 elements.

### D14. Openings that touch the wall outline are subtracted with a boolean
- **Decision:** Wall elevation profiles keep interior openings as holes. Openings that touch or cross the outline (doors at the base) or overlap other openings are subtracted with `PolygonBoolean.difference`.
- **Why:** A hole touching the outer loop produced non-manifold solids, and IFC exported them as open face sets. The walls are now closed, and IFC exports them with `Closed = .T.`. Tests check watertightness and volume.

### D15. Crop regions and 1:200 for the reference project's sheets
- **Decision:** Courtyard House plans, RCPs, elevations and sections placed on A1 sheets are cropped to the building and grids and drawn at 1:200.
- **Why:** At 1:100 the building (about 50 × 56 m) does not fit an A1 sheet next to the title block. Uncropped views also pulled in topography and property lines.

### D16. Dialog sizing uses ideal widths with fitted presentation
- **Decision:** Every dialog declares `minWidth` and `idealWidth` (and heights where it contains lists), and sheets use `.presentationSizing(.fitted)`.
- **Why:** Visual QA showed sheets narrower than their content, which clipped titles and fields.

### D17. Element revisions are process-unique content stamps
- **Decision:** `Element.revision` gets a fresh value from a process-wide atomic counter whenever an element is created or changed by a commit. The counter is seeded from the clock (milliseconds << 20). Revisions below 2^40, written by earlier builds, are re-stamped on load.
- **Why:** Caches key on `(id, revision)`. With per-element counters (1, 2, 3…), undo restored old revision numbers, and the next different edit reused a revision already cached for other content. The result was stale room areas and door sizes (found by the Domain test suite). Two open documents with the same element ids could also share cache entries. Now a revision identifies exactly one content, so undo can still hit the cache for restored states.
- **Cost:** Revisions are large and non-sequential. Tests that expected 1, 2, 3 now check that each new revision is larger than the last.

### D18. Closing a document tears down its data explicitly
- **Decision:** `ArcusDocument.close()` calls `DocumentState.tearDown()`. That cancels tasks and drops the model, undo history, tools and display lists. `windowWillClose` detaches the content view controller, and derived caches are purged when the last document closes.
- **Why:** Heap analysis (`heap`, `leaks --traceTree`) showed SwiftUI's focus and sheet bookkeeping sometimes keeping the last closed window's views, and through them the whole project, alive. App code can't break those framework references, so closing now empties whatever they hold. The QA harness checks that closed documents hold no project data.

### D19. Mirror and paste-to-level semantics
- **Decision:** Mirroring does not toggle a door or window's hand, because mirroring the host already mirrors the insert. Mirrored components get the rotation φ − θ + π together with the mirrored flag. Paste to another level moves top constraints to the level at the same relative elevation, or converts them to an unconnected height.
- **Why:** Tests that compare placements against the exact geometric reflection showed hinge sides and component orientations coming out wrong, and pasting walls to an upper level was rejected.

### D20. Overlay passes never paint a background
- **Decision:** `GraphicsRenderer` paints the canvas colour only when the pass's `RenderOptions.background` is set. Tool and drag preview passes draw with no background.
- **Why:** In dark appearance, every preview pass (the wall rubber band, door placement, drag-move ghost, sketch lines) painted the dark canvas colour over the whole visible area. The view vanished while any tool or drag was active. It was found by the interaction QA's pixel check, and there is a regression test in `RendererTests`.

### D21. Dragged and moved elements are excluded from snapping; moving a wall keeps its joins
- **Decision:** `ToolContext.snapExclusions` holds whatever is being dragged or moved, and `SnapIndex.snap` ignores it. `ElementOperations.transform` moves the joined ends of walls that did not move to the moved wall's new centerline (corner and tee joins; it respects disallowed joins and pinned walls).
- **Why:** A dragged wall snapped to its own original midpoint, so short drags "didn't move". Moving one wall of a room opened its corners.

### D22. Temporary hide/isolate is framed on the canvas
- **Decision:** While temporary hide/isolate or Reveal Hidden is on, the canvas shows a coloured frame and a label ("type HR to reset").
- **Why:** Typed aliases such as `HH` and `HI` hide elements instantly. Without a clear indicator this is indistinguishable from elements vanishing.

### D23. `RT` is Room Tag and `EL` is Spot Elevation; Elevation view moves to `EV`
- **Decision:** The default alias `EL` now starts Spot Elevation and `RT` starts Room Tag. The Elevation view marker, which held `EL`, uses `EV`. It stays on the View ribbon, in the Document menu and in Command Search.
- **Why:** Switchers type `EL` for spot elevations and `RT` for room tags. User alias overrides are stored by alias and applied on top of the defaults, so anyone who bound `EL` themselves keeps that binding.

### D24. A Revit-familiar shell: ribbon, contextual tabs, Options Bar, Properties, Project Browser
- **Decision:** The command deck is a ribbon with the tab and panel names switchers expect (Modify, Architecture, Structure, Insert, Annotate, Massing & Site, View, Manage). A green contextual tab ("Modify | Place Wall", "Modify | Sketch Floor Boundary", "Modify | Walls") appears while a tool runs or elements are selected, with Draw and Mode (Finish/Cancel) panels. A separate Options Bar is always present. Properties shows the Type Selector, an instance bar ("Walls (3)", "New Walls", "Floor Plan: Level 1") and Edit Type, and is never blank. The navigator is called the Project Browser. The window subtitle names the active view. Dense panels (Modify, Clipboard, the Modify tab's View panel) are icon-only, as in the tools users come from, so the contextual tab fits a laptop screen.
- **Why:** Research from two textbooks and a six-hour course (Docs/RevitParity.md) showed switchers navigate by these names and places first. The styling is Arcus's own: SF Symbols, Liquid Glass floating controls, macOS 27 sidebar and toolbar conventions. No Autodesk assets or text are used.

### D25. Selection modifiers default to the BIM convention
- **Decision:** ⌘-click adds and ⇧-click removes (window selections too). Settings ▸ Selection offers the Mac convention (⇧ adds, ⌘ toggles). ⌃-click is left to macOS as a right-click.
- **Why:** In the tools users switch from, Ctrl adds and Shift removes; ⌘ is the Mac equivalent of Ctrl.

### D26. Snap overrides and aliases follow BIM habits
- **Decision:** `SE`, `SM`, `SI`, `SN`, `SC`, `SP`, `ST`, `SQ` restrict the next pick to one snap; `SO` turns snapping off for it; ⇧ constrains drawing to horizontal or vertical; Tab cycles snap candidates while drawing. Section moved from `SE` to `SX` and Straight Stair from `ST` to `SR`. Zoom commands use `ZO` (out 2×), `ZS` (sheet size), `ZP`/`ZC` (previous pan/zoom). Select Previous is ⌥⌘← because ⌃← switches Spaces on macOS.
- **Why:** Typed snap overrides are muscle memory for switchers and would otherwise start the wrong command.

### D27. 2D views render with Metal 4; CoreGraphics remains the reference
- **Decision:** Plans, sections, elevations, drafting views and sheets are drawn by `ArcusCanvasMetal` (a retained GPU scene; pan, zoom and highlight only update uniforms and small tables) when the GPU supports Metal 4. Canvas2DView keeps event handling, draws the backdrop (canvas colour, sheet paper, underlays) beneath the GPU layer and the interactive overlays in a transparent layer above it. PDF export and printing keep using `GraphicsRenderer`, and `ARCUS_CANVAS=coregraphics` forces the CoreGraphics path. The GPU view renders nothing while its window is fully occluded.
- **Why:** The measured frame cost fell from 7–16 ms (CoreGraphics) to about 0.05 ms CPU and 0.5 ms GPU on the 20,000-element model, with pixel parity tests against CoreGraphics. Keeping CoreGraphics for vector output avoids rasterising PDFs.

### D28. The 3D viewport uses Metal 4 with a classic fallback; MetalFX only when frames are slow
- **Decision:** The 3D renderer uses MTL4 command queues, allocators, argument tables and an on-disk pipeline archive when `supportsFamily(.metal4)`, otherwise the classic API; both use residency sets, memoryless MSAA/depth and GPU-private scene buffers. Shadows, ambient shadows, silhouettes and a Realistic style are per-view Graphic Display Options. MetalFX spatial upscaling engages only while orbiting when full-resolution frames exceed 5.5 ms.
- **Why:** On the development Mac the upscaled path was slower than native rendering; it helps only on slower GPUs or very large windows.

### D29. Revit models arrive through an open exchange file, never by reading RVT/RFA
- **Decision:** A companion add-in (`Tools/RevitBridge`, public Revit API) writes `.arcusx`, an open JSON format with a published schema; Insert ▸ Import Revit Model turns it into native elements and families with stable identities, so re-imports update in place. RVT/RFA files are inspected only at the container level (release, embedded preview). Direct import compiles only against a licensed ODA BimRv SDK, gated like DWG.
- **Why:** The project must not reverse-engineer proprietary formats or imply compatibility it doesn't have, but users still need their existing models and families editable in Arcus.

### D30. Project schema 3
- **Decision:** One schema bump (2 → 3) covers the parity additions: ramps, extrusion roofs, shape points, solid joins, curtain wall data, openings, scope boxes, cameras, colour schemes and legends, area-scheme rules, dimension string styles, array specs, graphic display options and templates. Every new field decodes with defaults, so schema-2 files open unchanged (tested with a real schema-2 document); schema-3 files are refused by older builds with the usual "newer version" message.
- **Why:** A single, documented bump is easier to reason about than one per feature.

### D31. Wall ends dropped on another wall's end join it
- **Decision:** When a wall end (drawn or grip-dragged) lands within 1.5 × half the thickness of another wall's location end, it moves onto that location end, so a corner join forms. Ends in the middle of a wall already form tee joins and are left where they were put.
- **Why:** Users aim at the corner they can see, which snaps to a face corner. The walls then stayed unjoined and overlapping, which reads as "walls don't snap". Found by a QA step that draws with real canvas events.

### D32. Visible geometry wins snaps; parallel snapping; screen-space tolerances
- **Decision:** Wall location lines stay in the snap index as hidden reference geometry, but snap only when no visible geometry (faces, layer lines, lines) is in reach, so a line drawn to a wall lands on its face. While drawing, the rubber band snaps parallel or perpendicular to visible lines near the pointer or the start point, and to lines the pointer passed over recently (the last four, forgotten when the tool changes). Angle increments, parallel and perpendicular engage only within 6 screen points of the pointer, instead of a fixed 3°. The wall-join rule (D31) applies only when the end lies on the other wall itself, at its end.
- **Why:** Reported: model lines didn't snap to wall faces (the hidden centre line's perpendicular snap outranked the face), there was no parallel snapping, and walls snapped from a distance (a 3° tolerance is metres away on long lines, and the D31 zone was in metres, so it grew on screen when zoomed in).

### D33. Drawing, placing and dragging follow the reference recording
- **Decision:** Modelled on a screen recording of the reference workflow (walls, model lines, doors; drawing and dragging):
  - **Snap engine** (`Application/SnapEngine.swift`) in priority order: point snaps on visible geometry, then crossings of guides, then nearest, then a single guide, then free.
  - **Guides:** extensions of building and drafting lines (dashed, from far across the view), horizontal/vertical through the start point, parallel/perpendicular to nearby or recently hovered lines, and the line under the pointer.
  - **Increments:** lengths along guides and free rubber bands round to a zoom-dependent step (the smallest round value ≥ 8 pt: mm/cm/dm/m steps, or 1/16"…10').
  - **Status bar:** names what is snapped, e.g. "INTERSECTION of EXTENSION of [Lines : Model Lines] AND VERTICAL", "ENDPOINT of [Walls : Basic Wall : …] AND HORIZONTAL".
  - **Rubber bands:** show an angle arc from the horizontal, and distances to the nearest parallel lines on each side.
  - **Doors and windows:** show distances along the host to the nearest walls (or host ends) and pull to the middle between them; a typed value places them that far from the nearer reference.
  - **Dragging walls:** they move perpendicular to themselves in round steps (exact when locked onto a snap), with a live ghost of the joined walls stretching and live distances to references. Drags use only horizontal/vertical and extension guides.
- **Why:** Reported with a recording: walls, lines and doors didn't snap or drag the way users coming from the reference tool expect.

### D34. Drawing aids checked against the reference tool itself
- **Decision:** Behaviour observed hands-on in the reference application (running locally in a VM, empty project), applied:
  - **Cursor tooltip:** a short snap name beside the pointer after a brief pause ("Vertical and Extension", "Endpoint"), and "Drag to new position" while dragging; the full description stays in the status bar.
  - **Guides:** the start point's horizontal/vertical shows a double-arrow marker; the guide reach is small (6 pt on screen).
  - **Angle arc:** measured from the previous segment when chaining walls or lines (a straight continuation is 0°), otherwise from the horizontal; no arc at 0°.
  - **Grips:** filled blue circles.
  - **Dragging:** a dashed guide runs through the grab point along the move, a little past both ends.
  - **Alignment:** drawing beside a parallel wall or line offers a guide square to the rubber band through each of its ends, so the new element stops level with it ("Vertical and Alignment").
  - **Axis alignment:** any placement or rubber band that lines up horizontally or vertically with a nearby element centre or line end (within 6 pt, up to 600 pt away) is held on that axis with a dashed guide, whatever the element's size — a 6×6 post is too short for an extension guide but still aligns by its centre and corners.
  - **Door and window previews:** the distances stand off the wall face on the cursor's side, and the insert steps so the nearer distance is a round value for the zoom (the pull to the middle still wins near it).
- **Why:** Requested: "use the Revit … and find out how everything works and apply those to Arcus". Only observable behaviour was studied; no files, formats or assets from the reference tool were used.

### D35. Mac-native shell: tabs in the toolbar, project in the sidebar, floating tool options
- **Decision:**
  - **Toolbar:** the ribbon tabs (and the contextual "Modify | …" tab and minimize control) sit in the window toolbar; the window title is hidden. When the toolbar is too narrow for every tab, the task tabs fold into one menu and the contextual tab stays.
  - **Sidebar header:** the project name, an Edited badge and the active view, with a menu for Project Information, Duplicate, Move To and Show in Finder.
  - **Ribbon panels:** rounded groups under the toolbar; every ribbon, draw, mode, tab and bar control has hover and press feedback.
  - **Options Bar:** a floating glass bar over the top of the canvas, shown only while a tool runs. The permanent "Modify" strip is gone.
  - **Bottom bar:** view controls and status merged into one bar. View tabs appear only when more than one view is open, and messages appear at the bottom of the canvas.
  - **Materials:** layer and parameter material choices use a searchable picker (type to filter; arrows and Return choose). The Materials window has a searchable list grouped by class, a shaded preview, a color well, a palette and a transparency slider. New materials start from a name, a class and a color.
- **Why:** Requested: the tabs moved up, the project name in the sidebar, less space taken by the Modify strip, hover effects, searchable materials, a color for new materials, and a more native macOS look.

### D36. Cameras are 3D views with a full lens; navigation is Blender-style
- **Decision:**
  - **Camera views:** a camera is a 3D view whose `Camera3D` carries the pose plus optional near clip, far clip (on/off and distance) and a paper crop size (frame aspect). Any perspective 3D view, and any 3D view placed with a level, counts as a camera, so an orthographic camera keeps its plan glyph (now with the frame's aspect and the far clip line) and its eye/target grips. Focal length is 35 mm-equivalent against the 24 mm frame height (vertical angle), linked to the field of view; roll is derived from the up vector, so no extra state can disagree with it. Properties edit all of it through ordinary parameter transactions (new *Camera* group).
  - **Camera frame:** when a camera view crops (on for new cameras), the viewport shows the frame and the camera's angle spans the frame height, not the window; the renderer widens the angle for the whole view instead of changing the saved camera.
  - **Clip planes:** a finite far clip uses a reversed-Z projection with a far plane (`depthA`, `depthB`), which clips drawing and picking alike; the post-processing depth linearisation takes the same terms.
  - **Navigation:** middle-drag orbits, `⇧` pans, `⌃` dollies; `⌥`-left-drag emulates the middle button; a two-finger swipe orbits. The previous BIM-style scheme (middle-drag pans) stays as a *Middle Button* preference. Keys use the numeric keypad, `⇧F` and `⌃⌥` menu shortcuts only, so they never collide with typed aliases or numeric entry.
  - **Lock Camera to View:** on by default in camera views (navigating moves the camera, committed as one undo step when a navigation ends, detected by the viewport's settle debounce plus `isNavigating`), off elsewhere (navigating a view that looks through a camera leaves it). The active camera and the locks are per document session, not saved.
- **Why:** Requested: "camera perspective like Revit but with complete control of the camera like Blender", with cameras manageable from the sidebar. Only observable behaviour of the reference tools was followed; no assets or formats were used.

### D37. Drawing, placing and moving in 3D views on a level work plane
- **Decision:**
  - **Work plane:** tools started in a 3D view run on a level's plane: by default the level of the most recently active plan view, else the lowest level; the Options Bar shows a Work Plane picker while a tool runs in 3D (changing it restarts the tool on the new level). Move, Copy and the other selection tools use the selection's level until a work plane is picked.
  - **Same tools, plan context:** the 3D view drives the plan tool instances through the level's floor-plan `ToolContext` (`WorkPlane3D` maps the pointer ray to the plane; snapping uses that plan's snap index with the tolerance scaled to the depth under the pointer). Doors, windows, Split, Align, Trim and Tag use the picked surface point, so a door follows the wall face under the pointer. The GPU-picked element leads the hit candidates, followed by the plan elements under the plane point.
  - **Feedback:** previews, guides, temporary dimensions, the snap marker, a small grid patch of the work plane and the cursor tooltip are drawn projected onto the plane in a transparent layer above the viewport. Typed values work as in plan.
  - **Selection in 3D:** click and Shift/⌘-click select as before. Dragging an already-selected element moves the selection on the horizontal plane through the grab point (walls perpendicular to themselves, as in plan) with snapping to its level's plan geometry, a live ghost and a typed distance. Dragging anywhere else still orbits. Arrow keys nudge a selection (along the world axis nearest the arrow's screen direction; Shift for larger steps); with nothing selected they stay camera keys. Delete deletes, Escape clears, letters type command shortcuts (WA, DR, MV …).
  - **Layering:** the viewport module only exposes rays, projection, picking and a `pointerHandler` that sees left-button and editing-key events first; the camera keeps middle/right buttons, scroll, gestures and navigation keys.
- **Why:** Requested: "everything should work in 3D mode too", and selecting floors, ceilings and other elements and moving them with snapping in 3D and 2D.

### D38. Unit-aware standard content; imperial by default
- **Decision:**
  - **Imperial first:** the new-project flow and onboarding default to Imperial (feet and fractional inches); Metric stays one click away. Imperial projects get ARCH D sheets and 1/8" or 1/4" plan scales.
  - **Types per unit system:** `StandardContent` (called at the end of `ProjectTemplates.populate`) adds imperial or metric wall, floor, roof and ceiling assemblies (`BuildingTypesLibrary`), door and window families (`OpeningLibrary`) and column families (`ColumnLibrary`), each with nominal sizes and names for that system (`36" x 80"`, `W10x49`, `HSS8x8x1/2` / `900 x 2100`, `HEB 200`, `ISMB 300`, `230mm Brick Wall`). In imperial projects the base template's metric-named types are converted in place, and `ProjectTemplates.Ids` keeps their old keys pointing at the converted types so code that looks content up by key works in both systems.
  - **Existing projects:** Manage ▸ Load Standard Types adds the standard types for the project's current units that it lacks (by name); nothing existing changes.
  - **Materials:** `MaterialLibrary` holds 428 original materials (classes, approximate sRGB colours, transparency, one-line descriptions, a region tag, including Indian, European, East Asian and U.S. materials). New projects start with a curated ~100 plus whatever their standard types use; Manage ▸ Materials ▸ Add from Library adds more, skipping names the project has.
  - **Column profiles without a format change:** I/H shapes are 12-point extrusion polygons; hollow sections are a solid extrusion minus a void extrusion, which the evaluator already cuts exactly (the result keeps its hole). Plan cut fills and outlines of columns now draw profile holes (`ComponentGeometry.planLoops`). No new `FamilySolid.Profile` case, so project and family files stay readable by current readers.
- **Why:** Users expect a template with the doors, windows, assemblies and sections they specify every day, named the way their market names them. Adding profile kinds would have needed a family and project format bump for shapes the existing forms already express.

### D39. DWG without an SDK licence: run a converter the user installed
- **Decision:** Builds without the ODA Drawings SDK link and import DWG through a separately installed converter: ODA File Converter (free app from the Open Design Alliance) or LibreDWG's `dwg2dxf`. Arcus only looks in the usual install places (`/Applications`, `~/Applications`, Homebrew and MacPorts `bin` folders) or at a path chosen in Settings ▸ DWG Converter, copies the DWG into a private temporary folder, runs the tool as a separate process (argument array, timeout, cancellation), and reads the resulting DXF with its own DXF reader. Links keep the original `.dwg` and reload by converting again. Without a converter or the SDK, the DWG dialog explains both options with install steps and offers DXF; nothing is downloaded and no link is opened. The compile-time SDK route is unchanged.
- **Why:** The product owner asked for DWG import without an SDK licence, "like RVT" (D29): an open intermediate format produced by a separate tool, not a reverse-engineered reader. Running the tool as a process keeps GPL code (LibreDWG) and ODA's binaries out of Arcus, and the report and dialogs say that the third-party tool did the conversion.

### D40. Site tools store their data on existing elements
- **Decision:** Sub-regions and graded regions are toposurfaces: a sub-region has a `hostID` to its surface, a plan `boundary` and a `materialID` (new optional `TopographyData` fields). Graded Region demolishes the existing surface in the view's phase and creates a copy in that phase. Site Settings (contour interval, primary every N, show contours) are parameters of the Project Information element. Parking layouts are model lines in "Parking Stripes"/"Parking Wheel Stops" line styles, grouped, with the stall count in the group's Comments. Wall sweeps, slab edges and roof soffits are optional fields on `WallData`, `SlabData` and `RoofData` with instance parameters, meshed by `HostedProfiles`.

### D44. Keyboard focus, aliases, two-stage cancel and context menus
- **Decision:**
  - **Text input wins, app-wide.** While a text field, search field, inline editor or dialog text control has the keyboard, canvas keys run nothing: no alias, tool shortcut, `Return`-as-Finish or `⌘A` element Select All. AppKit and SwiftUI fields are detected by their field editor (`TextInputFocus`); inline editors that are shown before they get focus (rename fields) register with `.inlineTextEditing(_:id:focus:)`, and a key reaching the canvas meanwhile is handed to the editor. The routing decisions live in `CanvasKeyRouter` (Application, unit tested).

The "Z aliases never execute" report was most likely the echo: the old buffer ran `ZF`/`ZE` (a no-op on a view already zoomed to fit) but the status text kept "Shortcut: Z…". Zoom and snap-override aliases don't end the active tool.

Arcus has no work plane grid in 2D, so `SW` snaps to grid intersections; `SX` (points) means end and centre points; `SR` widens the capture radius four times; `SZ` snaps to endpoints.
  - **Two-stage cancel** (`ToolLifecycle.escape`) is used by `Esc` and context-menu Cancel: step, then tool (selection kept), then selection. Sketch mode never ends on `Esc` (previously a sketch tool answering "exit" was cancelled). A Move/Copy preview cancel keeps the selection.
  - **Selection commands without a selection** (Move, Copy, Rotate, Mirror, Array, Scale, Pin, Unpin, Delete) wait for one: select, then `Return` or Finish. `Return` in Modify repeats the last creation/modify command (`ToolLifecycle.isRepeatable`; views, undo, clipboard and snaps are never repeated).

  - **Selection after Undo is kept** (elements that still exist stay selected), deliberately unlike the reference tool, which clears it: keeping it lets the user retry an edit and matches macOS editors. **Pinned elements**: Move and Delete are refused with a message and nothing changes; the selection is kept (not cleared); an unpinned element joined to a pinned one moves and the pinned one stays (joins to pinned walls never drag them). Delete now reports pinned elements it kept (the message was recorded but never shown).

- **Why:** Backlog ARCUS-001/002/003/024/028/032/040/041/052/053/055/056/057/065–069/078/091: typing into a rename field started tools and selected all elements, context-menu Cancel left the chain running, Space flips during door placement were overwritten by the next pointer move, and menus, defaults and options differed from what BIM users expect.

### D49. Toposolids on topography elements; BIM-style navigation by default; compact Modify panels beside wall panels
- **Decision:**

### D52. Line-family fill patterns: cut/surface patterns per material, standard library, editable, same in Metal/PDF/DXF
- **Decision:**
  - **Patterns are line families.** `FillPatternData` gains optional `families: [HatchFamily]` (angle, origin, shift, spacing, dashes; millimetres — paper for drafting, model for model patterns) and `description`; `kind` stays as the procedural fallback and the pattern of older files, which decode unchanged and are upgraded in place by `FillPatternLibrary.ensureStandard` when their name is a standard one. `HatchGenerator` (Domain) turns families into segments and dots clipped to the region (even-odd, holes stay empty), anchored at the view origin; `HatchCache` memoises per (region, pattern, scale). Over-budget hatches (> 60k marks) fall back to the procedural kind; denser than two device pixels they tint (CG) or fade (Metal stroke flag bit 1, spacing carried in `dash`).
  - **Standard library** (`FillPatternLibrary`, 80+ patterns: drafting section hatches — concrete, block, brick, stone, earth, sand, gravel, batt/rigid insulation, framing/finish wood, steel, aluminium, ANSI-style 31–38, glass, tile, gypsum…; model surface patterns — brick and block bonds, tile modules, paving, boarding, ceiling grids, roofing) loads into new projects and is addable to old ones. Names of the 14 legacy kinds are kept.
  - **Materials** have Cut Pattern / Cut Pattern Color and Surface Pattern / Surface Pattern Color (Materials window, Graphics section; catalog parameters `material.cutPattern`…). Every library material gets defaults by name and class (`MaterialPatternDefaults`). Walls, floors, roofs and ceilings have a type **Coarse Scale Fill Pattern/Color**; filled region types a **Fill Pattern** (project pattern reference) with Color and Background; `region.pattern` text stays for older types.
  - **Rendering order** (lowest first): category poché/class hatch → material pattern and colour → type coarse fill (coarse only) → view override (category → subcategory → filters → element, `GraphicOverride.cutPatternID/surfacePatternID` beside the legacy kinds). Plan cuts per wall layer (fine), section cuts per wall layer (medium/fine, `wallLayerCutFills`), slabs/columns/toposolids use the element's type; floor and ceiling finish materials draw their surface pattern in plan. Metal draws hatch lines as pen-1 strokes over the background fill, CoreGraphics/PDF as vector strokes, DXF as HATCH entities with pattern definition lines (group codes 53/43–46/49) in drawing units.
  - **Fill Patterns dialog** (Additional Settings) lists patterns with previews and use counts: New/Edit (text editor with live preview, Start From… a standard), Duplicate, Delete (users fall back to category defaults), Import…/Export… in Arcus's documented text format (Docs/FillPatternFormat.md), Add Standard Patterns. Every change is one undo step. `FillPatternMenu` is the searchable picker used by materials, type properties, V/G pattern columns and Override Graphics in View.
- **Why:** Cut graphics were one fixed procedural hatch per material class and not editable; working drawings need material-specific section hatches and model-scale surface patterns that print identically in PDF and DXF, with per-view overrides in the D48 order.

### D54. The whole window is the canvas; the shell floats over it as Liquid Glass pills
- **Decision:**
  - **No toolbar, no title bar.** The document window is `.fullSizeContentView` with a transparent title bar and no `NSToolbar`; the canvas (2D, 3D, sheets, schedules) fills the window edge to edge and every piece of chrome floats over it on a `GlassShieldView` (`NSGlassEffectView`, or an opaque window-coloured panel with a separator border under Reduce Transparency / Increase Contrast): the left sidebar and the Mac Spacious inspector (16 pt continuous corners, D50), the ribbon tab pill and the controls pill in the top row, the ribbon strip (16 pt), the tool Options pill, one small pill per open view, the bottom pill (capsules), and the canvas HUDs (navigation bar, toasts, ⌘K). 10 pt margins throughout. A shield is a real AppKit view above the canvas: clicks and wheels over it stop there (a wheel over a pill never zooms the drawing); a mouse-down on a pill's bare surface drags the window, as a toolbar would.
  - **Traffic lights in the sidebar.** The window's standard close / minimize / zoom buttons are moved (`standardWindowButton`) into a `TrafficLightsView` at the top-left of the sidebar; the group answers the buttons' hover query so the glyphs light up together. When the sidebar is collapsed (sidebar button, ⌥⌘S, View menu) it becomes a strip in the top-left corner holding the lights and a show-sidebar button, and the tab pill slides left to follow. AppKit re-tiles the buttons on some window events, so the controller re-places them after every window update (a no-op when nothing moved) and returns them to the title bar when no host exists.
  - **Rows.** Top row: tab pill (Architecture … Modify, the green contextual tab, the minimize chevron) at the left of the content span, controls pill (undo/redo with history menus, previous view, 3D, ⌘K, workspace menu, inspector toggle) at the right. Second row: the ribbon strip, hidden when the ribbon is minimized (the tab pill stays). Third and fourth rows, only when they apply: the Options pill while a tool runs, and the view-tab pills when more than one view is open. Bottom: the view controls, status and selection in one pill. The content span runs from the sidebar (or the strip) to the inspector or the window edge, so the pills keep clear of the docks. The tab pill compacts its tabs into one menu when the row is too narrow; in a window too narrow for even that beside the full controls pill (both docks at 980 pt) the controls pill drops previous view and 3D into its menu. The status bar drops the cursor coordinates before anything else when the bottom pill is narrow.
  - **Canvas insets.** `ShellLayout` (Application, tested) yields the rows' frames and the top/bottom/leading/trailing insets; `CanvasContainerView` turns them into `additionalSafeAreaInsets` over what the window contributes (the title bar), so zoom to fit centres in the visible region, the 3D orientation cube and the navigation bar sit under the top rows (the navigation bar below the cube in 3D views) and schedule tables lay out inside the safe area.
  - **Removed.** The NSToolbar, toolbar customisation and the quick-access toolbar commands (every command stays reachable from the ribbon, the controls pill, ⌘K and the menus); `UndoHistoryToolbarItem` became the SwiftUI `UndoHistoryMenu`.
- **Why:** The product owner's wireframe: the whole window is the drawing, with a full-height floating sidebar carrying the traffic lights, a tab pill and a controls pill in the top row, the tab's detailed items on a bar under them, all Liquid Glass with the drawing showing through. AppKit shields were kept over SwiftUI-only glass so that input containment is provable in the QA harness (`QAInteraction+Shell.swift`, "W4-WIRE" steps) and the geometry stays a pure value with tests (`ShellLayoutTests`).


### D55. The app is called Arcus
- **Decision:**
  - **Name and identifiers.** Product, app bundle, SwiftPM modules and targets (`ArcusGeometry` … `ArcusCanvasMetal`, `Arcus`), bundle id `com.local.Arcus`, project packages `.arcus` (`com.local.arcus.project`), family packages `.arcusfamily` (`com.local.arcus.family`), the exchange format `.arcusx` / `arcus-exchange`, the IFC property sets `Arcus_Parameters` / `Arcus_TypeParameters`, build variables `ARCUS_*`, and backlog ticket ids `ARCUS-###`.
  - **No compatibility layer.** The working name Plinth was never released, so Arcus reads and writes only its own formats: no legacy UTIs, file extensions, manifest ids, exchange ids, IFC property sets or preference migration.
  - **"Plinth" the building part stays.** Column bases and cabinet kick-plinths keep the architectural term in the column and component libraries.
  - **Icon.** `script/make_icon.swift` draws an original icon: a semicircular stone arch of nine voussoirs with an amber keystone, on piers and a base line, over a blueprint-blue squircle with a drafting grid, a dashed setting-out circle and a glass highlight. Fine detail is dropped at 16/32 px.
- **Why:** The product owner named the app Arcus for good. "Arcus" is Latin for arch, which gives the icon its subject.
