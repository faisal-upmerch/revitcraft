# Performance

All numbers were measured on 2026-09-25 on a MacBook Pro (Mac17,8, Apple M5 Pro, 18 cores, 48 GB), macOS 27.0 (26A428), with a release build. They are single-machine measurements, not guarantees. See "8 GB Macs" below for what to expect on smaller machines.

Three sources of numbers:

1. **`arcus-bench`**: headless engine benchmarks on generated fixtures, reporting medians over repeated runs. Raw output: [Benchmarks/bench-release.json](Benchmarks/bench-release.json).
2. **In-app QA harness**: the real app, windows and Metal included (`script/qa_capture.sh all`). It records per-step timings, 3D frame times and the process memory footprint in `results.json`.
3. **Instruments**: `os_signpost` intervals under the Points of Interest category, subsystem `com.local.arcus`, recorded with `xctrace` during the QA runs.

## What changed because of these measurements

Benchmarking the stress fixture exposed several quadratic paths. They were fixed, and the fixes are covered by tests (see the [Decision log](DecisionLog.md), D12, D13 and D17):

| Operation | Before | After |
|---|---:|---:|
| Stress floor plan display list | 13.7 s | 0.13 s |
| Stress 3D meshes (all elements) | 13.9 s | 0.08 s |
| Stress: move all 10,000 walls | 37.8 s | 0.10 s |
| Courtyard House, all 10 schedules | 603 ms | 20 ms |
| Courtyard House, Door Schedule | 257 ms | 9.9 ms |
| Courtyard House, Ground Floor plan display list | 58 ms | 5–7 ms |
| Courtyard House, 16-sheet PDF | 2.68 s | 1.08 s |

The causes were: every wall-join lookup sorted and scanned all walls (fixed by a spatial plan grid in `BIMModel`); room-boundary cache keys hashed the whole model on every lookup (fixed by per-snapshot content stamps); and schedule cells and tag labels evaluated every parameter of an element to read one (fixed by single-parameter fast paths).

## 8 GB Macs

Arcus was not run on an 8 GB Mac for this report. From the measurements above:

- A project like the Courtyard House needs about 100–350 MB, depending on how many views have been opened.
- The 20,000-element stress model peaked at 739–824 MB during long QA sessions. That leaves ample headroom on an 8 GB machine.
- Engine work is mostly single-threaded per view (view builds run off the main thread, one task per open view). As an estimate (not measured), expect roughly 1.5–3× the times above on a base M1 or M2.

Things that keep memory bounded:

- Derived geometry is cached per element and replaced on change. All derived caches are purged when the last document closes.
- Closing a document tears down its model, undo history, display lists and tasks, even if a framework briefly keeps a window shell alive.
- Reference drawings (CAD and PDF content) are content-addressed and shared between links.

## Reproducing

```bash
swift run -c release arcus-bench --out bench.json          # add --quick for 3 runs, --stress N to size the stress fixture
script/build_and_run.sh --no-launch && script/qa_capture.sh all build/qa   # app-level numbers in build/qa/results.json
```
